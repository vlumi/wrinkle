# Six shapes, 2026-10-15

> Followed by [2026-10-21](2026-10-21-shapes.md), after coalesced acks and batched fan-out appends doubled the highest sustained rate.

The protocol in [measuring.md](../measuring.md), every series three times, each backend from a freshly created stack (`FRESH=1`), in one session on one machine (`REPS=3 make measure-all`, 14:10 to 17:39 UTC). Medians of the three repetitions throughout. Raw runs: [go](2026-10-15-go.jsonl), [go-gateway](2026-10-15-go-gateway.jsonl), [java](2026-10-15-java.jsonl), [java-gateway](2026-10-15-java-gateway.jsonl), [elixir](2026-10-15-elixir.jsonl), [rust](2026-10-15-rust.jsonl).

- Commit: bfc6a78, with accounts, groups, contacts, end-to-end encryption, reactions, stickers, attachments, the connection limits and drain. The load is direct messages only, sealed as the clients seal them (see measuring.md).
- Monoliths: Go 1.27.2 and OpenJDK 25.0.4.1, one process each with all roles.
- Gateways: the Go and Java backends split into a gateway process and a services process over the internal RPC (`backends/go/split.sh`, `backends/java/split.sh`); the Elixir gateway (Elixir 1.20.4, OTP 29, Bandit) and the Rust gateway (Rust 1.99.0, tokio, axum) beside a Go services process. The measured process is the gateway; the services and fan-out run in the other, so a gateway's CPU is its own.
- Machine: MacBook Pro (Mac16,5), Apple M4 Max (16 cores), 48 GB, macOS 26.7.1; Docker Desktop with its default 16 CPUs and 8 GB, version 4.95.0 or earlier (it was updated to 4.96.0 after the run).
- Infrastructure: `infra/docker-compose.yml` as committed, with the default memory caps.
- Every run connected all its devices (no connect errors) and every received message decrypted.

## Idle connections

Resident memory at 500, 1000, 2000 and 4000 connections, the least-squares slopes, and the RSS baseline (the fit's intercept). Live memory as each runtime reports it after a collection: Go's heap and stacks, the JVM's pools (without Netty's direct buffers), the BEAM's process and system memory (which counts allocator carriers); Rust has no such figure.

| Shape | RSS at 500 / 1000 / 2000 / 4000 | RSS slope | Live at 500 / 4000 | Live slope | RSS baseline |
|---|---|---|---|---|---|
| Rust gateway | 21 / 39 / 67 / 124 MiB | 31 KiB | – | – | 4 MiB |
| Go gateway | 59 / 88 / 141 / 225 MiB | 50 KiB | 20 / 111 MiB | 26 KiB | 36 MiB |
| Elixir gateway | 131 / 113 / 166 / 245 MiB | 37 KiB | 77 / 143 MiB | 18 KiB | 95 MiB |
| Java gateway | 308 / 308 / 323 / 405 MiB | 32 KiB | 100 / 140 MiB | 12 KiB | 286 MiB |
| Go, all roles | 180 / 132 / 243 / 536 MiB | – | 21 / 116 MiB | 28 KiB | – |
| Java, all roles | 542 / 684 / 622 / 512 MiB | – | 135 / 172 MiB | 11 KiB | – |

- **The monoliths' resident memory measures the sign-in phase, not the connections.** Before every run the load generator signs its users in, and each sign-in hashes a password in about 19 MiB; the process keeps that memory, so its RSS is not monotonic in the connection count and its slope means nothing (Java's comes out negative). Their live slopes are unaffected. The gateways do no hashing; the services process beside them does, and is not measured.
- **The slopes scatter between repetitions.** Rust's RSS at 4000 connections was 124, 60 and 129 MiB, its slope 31, 10 and 31 KiB: the allocator returns memory to the system unevenly. The Go gateway's RSS slope ranged from 46 to 55 KiB; the live slopes moved by less than 2 KiB for every shape.
- **Live slopes rank the runtimes as before.** The JVM keeps the least per connection (11 to 12 KiB, plus Netty's direct buffers outside the heap, which is why its RSS slope is 32), the BEAM 18 KiB, Go 26 to 28 KiB (two goroutine stacks and its WebSocket library's buffers, [idle memory](2026-10-10-idle-memory.md)).

## Latency at fixed rates, 1000 connections

| Shape | 100/s: p50 / p99 | 500/s: p50 / p99 | Send RTT p50 at 500/s | CPU per 1000 msgs at 500/s | RSS at 500/s |
|---|---|---|---|---|---|
| Rust gateway | 86 / 141 ms | 88 / 189 ms | 39 ms | 239 ms | 28 MiB |
| Go gateway | 95 / 158 ms | 95 / 238 ms | 41 ms | 385 ms | 92 MiB |
| Java gateway | 91 / 150 ms | 97 / 206 ms | 42 ms | 404 ms | 331 MiB |
| Elixir gateway | 95 / 154 ms | 118 / 268 ms | 50 ms | 509 ms | 193 MiB |
| Go, all roles | 85 / 151 ms | 86 / 204 ms | 37 ms | 1542 ms | 147 MiB |
| Java, all roles | 90 / 154 ms | 93 / 203 ms | 39 ms | 2041 ms | 499 MiB |

Every shape delivered every message at 100/s and 500/s, in every repetition. At 1000/s every shape saturated: the load generator sent at the rate, sends timed out, and 65 to 74 % of the expected receipts arrived, at p50 around 19 to 20 s; at 2000/s, 30 to 34 %. The highest sustained step is 500/s for all six, set by the database, as on 2026-10-11 (ROADMAP.md, "Database ceiling").

The monoliths' CPU includes the services and the fan-out, the gateways' does not, so the two groups do not compare on CPU. The figure per message is higher at 100/s for every shape (the Java gateway's 767 ms against 404), since work that does not scale with messages, the timers and the JIT, is spread over fewer of them.

The Go and Java services differ in one step of the send path: before its transaction, Go reads the conversation row without a lock for the membership and block checks on every send, while Java remembers a direct conversation's members in a bounded in-memory map, since they never change. The Go monolith therefore makes one more read per message than the Java one.

## Reading it

- **Rust is the lean gateway on every axis it owns:** 124 MiB at 4000 idle connections against 225 to 405 for the others, a third of the Go gateway's memory under load (28 against 92 MiB), 62 % of its CPU per message, and the lowest latency of the gateways. Nothing in it was tuned.
- **The gateways are within 10 ms at p50, except Elixir at 500/s.** The path they share, the RPC to a services process and the same fan-out, dominates. Elixir's 118 ms at 500/s is 23 ms above the Go gateway's, steady across repetitions (117, 118, 122 ms), with the highest CPU per message; at 100/s it is level with the others. Where the time goes, Bandit's frame handling, the gRPC client, or scheduling, is not established.
- **The Java gateway is the Go gateway's equal under load** (97 / 206 ms, 404 ms CPU per thousand messages) at about three times its resident memory, most of it a baseline of almost 300 MiB.
- **The monoliths are the fastest shapes**, 86 and 93 ms p50 at 500/s, since they skip the internal RPC; the hop costs the split shapes 4 to 9 ms.

## Against 2026-10-11

Same machine and Docker Desktop allocation, but not the same infrastructure: the stack since gained a second Debezium connector (the user keyspace's outbox), object storage and the balancers, and the code gained everything listed above. The comparison is of the whole, not of the backends.

| Shape | 500/s p50 / p99, 10-11 → 10-15 | CPU per 1000 msgs at 500/s |
|---|---|---|
| Rust gateway | 84 / 246 → 88 / 189 ms | 277 → 239 ms |
| Go gateway | 94 / 574 → 95 / 238 ms | 454 → 385 ms |
| Elixir gateway | 110 / 437 → 118 / 268 ms | 470 → 509 ms |
| Go, all roles | 87 / 277 → 86 / 204 ms | 1379 → 1542 ms |
| Java, all roles | 87 / 230 → 93 / 203 ms | 1469 → 2041 ms |

The medians are within 8 ms and the tails shorter, though 2026-10-11 took one run per step and these the median of three. The monoliths' CPU per message rose, Go's by 12 % and Java's by 39 %: the services now check the key epoch and blocks on every send. Why Java's rose three times as much as Go's is not established. The gateways' fell or held, since none of that runs in them.
