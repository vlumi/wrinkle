# Three gateways and two monoliths, 2026-10-11

> These results predate accounts, groups and end-to-end encryption (commit 0b06d92; the connection limits and drain came later too). They are superseded by [2026-10-15](2026-10-15-shapes.md), every shape on the code with all of those, three repetitions each.

The protocol in [measuring.md](../measuring.md), each backend from a freshly created stack (`FRESH=1`), in one session on one machine. Raw runs: [go-gateway](2026-10-11-go-gateway.jsonl), [elixir](2026-10-11-elixir.jsonl), [rust](2026-10-11-rust.jsonl), [go](2026-10-11-go.jsonl), [java](2026-10-11-java.jsonl).

- Commit: 0b06d92
- Gateways: the Go backend split into a gateway process and a services process over the internal RPC (`backends/go/split.sh`); the Elixir gateway (Elixir 1.20.4, OTP 29, Bandit) and the Rust gateway (Rust 1.99, tokio, axum) with the same Go services process beside them. The measured process is the gateway; the services and fan-out run in the other process, so the gateway's CPU is its own.
- Monoliths, for reference: Go 1.27.2 and OpenJDK 25.0.4.1, one process each with all roles, as on 2026-10-10 but from a fresh stack.
- Machine: MacBook Pro, Apple M4 Max (16 cores), 48 GB, macOS 26.7.1; Docker Desktop 29.8.2 with 16 CPUs and 8 GB
- Infrastructure: `infra/docker-compose.yml` as committed

## Reading it

- **Rust is the lean one on every axis** that the gateway owns: less than half the Go gateway's resident memory at 4000 idle connections (78 against 167 MiB) and a quarter of it under load (22 against 90 MiB at 500/s), 60 % of its CPU per message, and the tightest tail. Nothing in it was tuned.
- **The three gateways are within 15 ms of each other at p50.** The path they share, the RPC to the same services process and the same fan-out, dominates; the gateway's own work is a few milliseconds. The tails differ: Rust 246 ms, Elixir 437 ms, Go 574 ms at 500/s. Go's 1061 ms p99 at 100/s was measured in the first run after the stack was created, a minute earlier, and did not recur at 500/s on the same stack; the 100/s step is the first after a fresh stack for every backend, and Go's was the only one with such a tail, so where it came from (the gateway, or Debezium and Kafka Connect warming up) was not established.
- **Elixir's memory per connection is not what the BEAM's reputation suggests here.** Each connection is a process holding a Bandit handler, and the WebSocket frames pass through Bandit's HTTP layer; the live slope of 37 KiB is the highest of the four, though the VM's accounting includes allocator carriers. The BEAM's strength, isolation and scheduling under load, is not what this protocol measures.
- **Go and Java, both from a fresh stack, are closer than [yesterday's comparison](2026-10-10-go-vs-java.md) said.** Java's p99 at 500/s was 491 ms yesterday, when it ran after Go on a stack that had grown by 36000 messages; today, from empty, it is 230 ms against Go's 277. Memory and the 200 MiB baseline stay as they were. Run order on a shared stack was a flaw of yesterday's protocol, fixed by `FRESH=1`.
- **The stack degrades as it grows.** Before the fresh-stack rule, the Go gateway measured 1.4 s p50 at 500/s on a stack holding 1.2 million user events; 94 ms from empty. Where the time goes, Debezium's binlog position, the outbox table, or the user log, is not yet known. Since these runs, outbox rows are deleted in the transaction that inserts them (commit 7d90a50), so the outbox table no longer grows; whether that removes the degradation has not been measured.

## What was found and fixed on the way

- grpc-go's server allows 100 concurrent streams per connection by default. The Go and Rust clients queue when the limit is reached; the Elixir client fails the call, which lost a third of the Elixir gateway's requests under a connect storm. The services process now allows 2^20.
- The Elixir gateway seemed to deliver late, at 3 s p50, until the Go gateway showed the same on the same stack: the environment, not the gateway.
