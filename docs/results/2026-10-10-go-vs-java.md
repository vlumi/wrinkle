# Go vs. Java, 2026-10-10

Both backends measured with the protocol in [measuring.md](../measuring.md) in one session on one machine: [Go](2026-10-10-go.md) at commit 90a9b77, [Java](2026-10-10-java.md) at commit 6f5853d, the same infrastructure for both. Both implement the same design against the same contract and pass the same conformance tests; both work on the same database, even with the same derived ids.

## Side by side

| | Go 1.27 | Java 25 |
|---|---|---|
| Resident memory, 1000 idle connections | 82 MiB | 274 MiB |
| Resident memory, 4000 idle connections | 215 MiB | 301 MiB |
| Memory per connection, slope | 46 KiB | 13 KiB (noisy, see below) |
| End-to-end p50 / p99 at 100/s | 69 / 118 ms | 78 / 162 ms |
| End-to-end p50 / p99 at 500/s | 66 / 173 ms | 97 / 491 ms |
| Send round trip p50 at 500/s | 19 ms | 28 ms |
| CPU per 1000 messages at 500/s | 1.37 s | 1.47 s |
| Highest sustained rate | 500/s | 500/s |
| Behavior at 1000/s | sends time out, fan-out delivers two thirds | sends stay at 30 ms, fan-out delivers a sixth |

## Reading it

- **Memory.** The JVM's baseline is about 200 MiB above Go's. Per connection, the Java figure is unreliable: its RSS fell between 1000 and 2000 connections, which a heap-sizing artifact explains and a per-connection cost cannot. Go's slope is credible but scatters by 10 KiB between runs. Neither per-connection number should be quoted without repetitions, and the Java one needs a fixed heap or a live-set measurement.
- **Latency.** Go's tail is tighter at every rate: p99 at 500/s is 173 ms against 491 ms. The send round trip is 9 ms shorter on Go at 500/s, which is the request path alone (gateway, one transaction through vtgate); the rest of the gap is in fan-out.
- **CPU.** Within 10 % of each other at the working rates, which is less than the run-to-run scatter seen so far. No conclusion.
- **Overload.** At 1000/s the database saturates for both (the Vitess container near five cores), but they fail differently. Go's request path competes hard enough for the database that sends time out; Java's request path stays fast while its fan-out worker starves. The difference is likely in how the two share their 32-connection pools between the gateway and the worker, not in the languages.

## What would sharpen it

- Repetitions (`REPS=3`) for the idle series, and a fixed JVM heap, before quoting memory per connection.
- A fan-out lag comparison from `wrinkle_fanout_lag_seconds`, which separates the worker from the request path directly.
- More CPU for the database, or vtgate and vttablet as separate processes, so the backends can be pushed past 500/s.
